The WikiMusic project is an non-profit community, with the goal of knowledge sharing and musical education, providing an open platform for exploring, sharing, and learning about music in all its forms.

If you like my work, please support me by [[https://bmc.link/jjbigorra][buying me a cup of coffee ☕]] so I can continue with a lot of motivation.

At its core, WikiMusic leverages the expressive power of Lisp (Guile Scheme) to build a dynamic interactive Music Gallery and Content Management System (CMS).

Whether you're a musician, educator, researcher, or simply a music lover, WikiMusic empowers you to:
- Discover music from diverse genres and traditions.
- Organize information with structured metadata and multimedia content.
- Contribute by adding new compositions, analyses, or educational materials.
- Learn through curated resources that connect music theory, history, and practice.

You can host your own version and database of WikiMusic, or visit the biggest one, mine over at:

[[https://wikimusic.jointhefreeworld.org][https://wikimusic.jointhefreeworld.org]]

WikiMusic leverages a database-backed architecture to ensure all content is easily searchable, linkable, and reusable. The user interface provides a seamless experience, inviting both beginners and experts to engage with the world of music collaboratively.

Join us in building an ever-growing library of musical knowledge — where every note tells a story.

This document is the project's README and its manual at once: it documents wikimusic, what it does, how to run an instance of it, how to work on it, and what administering one involves.  Everything below is here to be read, and the sections that describe a feature are the ones a contributor changes the behaviour of.  The same text is published as HTML at [[https://jointhefreeworld.org/manuals/wikimusic/][jointhefreeworld.org/manuals/wikimusic]].

* What Wikimusic offers

wikimusic is powered by: Guile Scheme, GNU Artanis, SQLite, Olive CSS, GNU Make, Emacs.

- *A gallery and a CMS in one*, built on Guile Scheme, GNU Artanis and SQLite,
  and written to be hacked: every piece of the interface is Scheme.
- *Songs, artists and genres*, each with a description written in Org mode,
  artworks, external sources, cross-references to the other entities, opinions
  and comments.
- *Song versions* that can carry an ASCII tab, a PDF, and a *Guitar Pro 5 tab*
  whose own header the page reads, which the page draws as notation and
  tablature, and which it plays back -- so a reader can see, hear and download
  the same file without leaving the page.
- *A responsive interface* -- the same shell on a phone and on a desktop -- with
  sorting, search and a subtle, icon-first tile-size control on every list.
- *Pretty error pages* for the refusals a reader actually meets (404, 403, 500
  and the rest), rendered by the application itself in the site's own shell.
- *Accounts and permissions*: sign-in, per-row ownership, and a super grant that
  overrides ownership for an instance's maintainers.
- *Everything out and back in*: a JSON dump of every content table and a
  rendered HTML archive of the whole instance, with an import route to load a
  dump into another instance.
- *A front page that is a way in*: what the place is called and what it holds,
  a line under it, a field that searches the collection, the two things a
  visitor came to do, the promises the community makes, the instance's own
  numbers, the genres to browse, and the newest songs and the newest artists --
  each shelf drawn with the tiles the list pages draw, so a tile on the front
  page and a tile on a list page are the same tile.
- *A page about the project*, at =/about=: what the community is, what a
  reader can do here, what it is built on, and the one control that asks for
  support -- which an instance that raises no money turns off.  The front page
  opens on what the place holds rather than on the introduction, so the account
  of the project lives here and is linked from every page's footer.
- *Nothing fetched from anybody else before a page can be read*: the type the
  interface is set in, the glyphs its controls wear and the picture the project
  shows of itself are files the instance serves, and the address they hang off
  is a deployment's to name.
- *Translated* into English, Dutch, Spanish and Japanese.

Wikimusic and Artanis are written using GNU Guile, one of the best implementations of Scheme language, which is what makes the following true of the whole interface:

- *Fully Customizable:* Hack the behavior and content of each UI element with Scheme code.
- *Cross-platform:* Runs anywhere that Guile Scheme can run, and exposes web endpoints, and is thus accessible from computers, phones, etc.
- *Free Software*: Contribute to its development or extend it with your own custom features.

* Running Wikimusic

If you are thinking of running Wikimusic yourself and hosting it on your own, here follow some tips.

Firstly, make sure you use the Guix package manager, whether as a standalone distro (Guix system) or on top of any other GNU/Linux distribution.

I include a ~manifest.scm~ in the repo so that it's easy to run the project if you use the Guix package manager.

If you want to run without Guix you should check that ~manifest.scm~ anyway since it will give you exactly the packages that you need.

** The environment file

For running wikimusic yourself, you'll need to define and load a module called ~(wikimusic env)~ where you add some required environment variables.  I recommend in the root of the project create a ~env.scm~ and exclude it from Git.

#+begin_src scheme
(define-module (wikimusic env))

(define-public encryption-key "a2ebe4c5-4a78-4490-af83-cfb05a285bf9")

(define-public signing-key "8d3a5bcc-973e-4f80-aa3d-33be33d6631c")

(define-public pingwing-url
  "my-pingwing-host")

(define-public pingwing-basic-auth-user
  "my-user")

(define-public pingwing-basic-auth-password
  "my-password")

#+end_src

The two keys are the instance's own secrets and they are what seals a session, so a deployment generates its own rather than reusing these; the rest name the mail service the instance sends through.

The same module is where an instance says what it says about itself.  Every one of these is optional -- an instance that names none of them is wikimusic, unchanged -- and each of them is read where it is used rather than written into the page that shows it:

#+begin_src scheme
(define-public source-repository-url "https://codeberg.org/jjba23/wikimusic")

;; Defaults to the README in the repository above.
(define-public manual-url "https://codeberg.org/jjba23/wikimusic/src/branch/trunk/README.org")

(define-public licence-url "https://www.gnu.org/licenses/agpl-3.0.html")

(define-public copyright-holder "Josep Bigorra")

;; Where the about page's donation control sends a reader.
(define-public donate-url "https://www.buymeacoffee.com/jjbigorra")

;; Whether the instance asks for support at all.  A deployment that raises no
;; money says #f here, and both the front page and the about page drop the
;; control -- and the note about what the money pays for -- rather than point a
;; reader at somebody else's page.  #f, "no", "off" and "0" all mean no.
(define-public show-donation? #t)

;; The picture a pasted link is previewed with, and the one near the front
;; page's closing: an address of its own, or a path on this instance, which is
;; what the project's own picture is.
(define-public social-image-url "/img/wikimusic.jpg")

;; Where the interface's own stylesheets, type and glyphs are read from.  Empty
;; -- which is what an instance serving them itself says -- reads them off this
;; instance; a deployment behind a CDN, or serving them from another path, names
;; the address they hang off.
(define-public assets-url "")

(define-public mail-sender-name "No Reply - Wikimusic")
(define-public mail-sender-address "noreply@mail.jointhefreeworld.org")
#+end_src

They reach the footer (where the code, the manual and the licence are linked), the about page and the front page (the donation control, the closing picture), every page's link preview, the address every stylesheet the page is set and painted with hangs off, and the mail the instance sends.  A value that is blank, or of something other than text, is read as unset: commenting a line out is enough to go back to the project's own value.

Two of them are read as rules rather than as values.  =show-donation?= is on unless the deployment turns it off, and =assets-url= means this instance's own copy unless it names somewhere else -- so an instance that never thought about either is wikimusic as it ships.

What an instance may name, and what each one falls back to, is written down in ~lib/wikimusic/config.scm~.  One of them is derived rather than defaulted: the manual's address is built from =source-repository-url=, so a fork that says where its code is read gets its own README link without having to name it separately.

Pingwing is a mail and notification solution written in Guile Scheme and also part of the jointhefreeworld project.  It's used in WikiMusic for password resets, among other notifications.  Find more about it here: https://codeberg.org/jjba23/pingwing

** The database, and the first user

You will need a database to be present in the root folder of the project (alongside ~app~, ~lib~, etc.).

Wikimusic uses SQLite by default but is also compatible with PostgreSQL and MySQL.

You can automate the creation of the database and the enabling of WAL mode for concurrent writes with ~maak init-db~:

#+begin_src sh
maak init-db
#+end_src

That task creates an empty database.  The schema is the migration kept in the tree, and applying it is what gives the instance its tables:

#+begin_src sh
guix shell -m manifest.scm -- sqlite3 wikimusic.db \
  < resources/migrations/sqlite/2026-04-19_23:14:00_init_wikimusic_schema.sql
#+end_src

Neither the server nor a task applies that migration on its own, so a fresh deployment runs the two commands once; a copy of the SQLite file, or a JSON dump loaded into a fresh database (see "Export, archival, and exchanging between instances"), are the other ways to arrive at the tables.

Upon starting a blank new wikimusic deployment you will have no users in the database, and there is no sign-up route: the first account is made from the shell, and it should hold two permissions -- =wikimusic:modify-permissions=, the super grant, and =wikimusic:user-create=, which is what the routes that make an account ask for.  The second is not covered by the first: a route asks for the permissions it names, and what the super grant overrides is ownership, not that (see "Accounts, permissions and ownership").

A password is stored as what ~hash-password~ derives -- Argon2id where this build's libgcrypt offers it, and PBKDF2-SHA256 otherwise -- with the algorithm, its cost and its salt written into the stored string itself.  Any characters may be in a password: the string reaches ~hash-password~ as a string and is never evaluated, and the salt is drawn fresh inside that call, which is why the ~users~ table's own ~salt~ column is left empty here.

#+begin_src sh
guix shell -m manifest.scm -- guile -L ./lib -L . -c \
  '(load "env.scm") (use-modules (wikimusic auth)) (display (hash-password "correct horse battery staple"))'
#+end_src

Take the string that prints, and insert the account with it.  The ~permissions~ column is read as a Scheme list and is never evaluated, so the permissions named there are the ones the holder holds:

#+begin_src sh
guix shell -m manifest.scm -- sqlite3 wikimusic.db <<'SQL'
insert into users (identifier, email, password, salt, permissions, username)
  values (lower(hex(randomblob(16))), 'you@example.com',
          '<the string hash-password printed>', '',
          '(wikimusic:modify-permissions wikimusic:user-create)', 'you');
SQL
#+end_src

The heredoc is quoted, so nothing in it is expanded by the shell: the hash
contains =$= and may as well contain anything else, and it is stored as the
bytes ~hash-password~ printed rather than as whatever a shell made of them.

The rest of the accounts are then made from the running site, by a holder of =wikimusic:user-create= (see "Accounts, permissions and ownership").  Sign in with the email and the password you hashed, and the instance is yours to fill.

If running locally, it's recommended to use ~localhost~ instead of ~127.0.0.1~ as this will work better with the authentication/authorization and other cookies.

** Hacking on it

If you are hacking away at the project, I would suggest using ~maak dev~ since this will effectively run the project with hot-reloading capabilities and it will use the default ~artanis.conf~ where we configure hostname, db path, etc.

Running the test suite is ~maak test~, and ~maak --list~ names every other task the project defines.  ~maak build-manual~ renders this document to HTML, and ~maak deploy~ copies that rendering to the instance that serves it.

The unit tests live in ~test/veritas/unit~, one file per area, and each is run by the framework with the deployment's own ~env.scm~ loaded.  What a spec needs beyond that -- being a *deployment* for the length of an assertion, when what it is proving is a switch a deployment turns off or a host it names -- is a helper module rather than a test of its own, and it lives outside the unit directory for that reason: ~test/support/deployment.scm~.

** Running it for real: a Shepherd service

If you are hosting this for production, I would suggest running Wikimusic as a Shepherd service/daemon.

You can alternatively just feel free to do this any other way, I recommend using the ~manifest.scm~ . Check ~maak.scm~ for every task the project defines.

Here follows an example of a Guix (Shepherd service):

#+begin_src scheme
(define-module (wolk-jjba wikimusic)
  #:use-module (gnu)
  #:use-module (guix))

(use-service-modules shepherd)

(define-public (wolk-jjba-wikimusic-service config)
  (list (shepherd-service (documentation "Run wikimusic as a daemon")
                          (provision '(wikimusic))
                          (requirement '())
                          (start #~(make-forkexec-constructor '("make"
                                                                "production-server")
                                    #:directory
                                    "/etc/wikimusic/job-clone/wikimusic/trunk"
                                    #:environment-variables '("GUILE_LOAD_PATH=/run/current-system/profile/share/guile/site/3.0"
                                                              "GUILE_DBD_PATH=/run/current-system/profile/lib"
                                                              "C_INCLUDE_PATH=/run/current-system/profile/include"
                                                              "GUILE_LOAD_COMPILED_PATH=/run/current-system/profile/lib/guile/3.0/site-ccache:/run/current-system/profile/share/guile/site/3.0"
                                                              "LIBRARY_PATH=/run/current-system/profile/lib"
                                                              "GIT_SSL_NO_VERIFY=1"
                                                              "PATH=/run/privileged/bin:/run/current-system/profile/bin:/run/current-system/profile/sbin")))
                          (stop #~(make-kill-destructor))
                          (auto-start? #t)
                          (respawn? #t))))

(define-public wolk-jjba-wikimusic-service-type
  (service-type (name 'wikimusic)
                (description "Run wikimusic as a daemon")
                (extensions (list (service-extension
                                   shepherd-root-service-type
                                   wolk-jjba-wikimusic-service)))
                (default-value '())))


#+end_src

* Accounts, permissions and ownership

Bewaking is a nice library to help you secure your web applications with Guile Scheme: https://codeberg.org/jjba23/bewaking

With bewaking we use secure tokens encrypted and stored in secure cookies (for browsers) and headers (for REST API)

If you want to be a super user in wikimusic your token will need to have the ~wikimusic:modify-permissions~ permission: it is what lets its holder change or delete any row, on any entity, whoever created it.  That grant overrides *ownership*, and only ownership -- a route also asks for the permissions it names, and the super grant does not stand in for those, which is why the account that hands out permissions needs ~wikimusic:user-create~ as well.

See more of the permissions here:

- wikimusic:song-create
- wikimusic:song-delete
- wikimusic:artist-create
- wikimusic:artist-delete
- wikimusic:genre-create
- wikimusic:genre-delete
- wikimusic:user-create
- wikimusic:user-delete
- wikimusic:modify-permissions

Wikimusic requires an authenticated session for performing administrative tasks such as creating/deleting the content of an instance.

** Who may edit what: permissions and ownership

A session is a sealed token that names the signed-in user and the permissions
they hold.  A route states the permission it needs, and a request that lacks it
is refused -- that is the *permission* half of the rule.  Wikimusic also has an
*ownership* half: a contributor may change what they created.

The rule, in one sentence: a request may change a row when the session either
holds the permission the route asks for *and* is the row's creator, or holds
=wikimusic:modify-permissions=, the grant that overrides ownership for every
row.  It is enforced on every mutation -- an entity's own edit route, and the
rows that hang off it: an artwork, an external source, a song version, a link
between two entities, and a comment's author.  There is no route that rewrites
or deletes a row without asking who made it.

- =wikimusic:modify-permissions= is the *super* grant.  Its holder edits and
  deletes anything, on any entity, regardless of who created it.  This is the
  permission to hand to the instance's maintainers.
- For everyone else, a mutation is allowed only when the row's =created_by=
  column names the session's user id.  A song's edit route, for instance, looks
  the song up and refuses when =created_by= is someone else.
- The check has two shapes for the two ways a route meets a row.  Where the
  page's own entity is at hand, =guard-owner= in =(wikimusic controller)= takes
  the row's =created_by= and answers #t when the change may go ahead.  Where the
  row has to be read first -- an artwork addressed by its own identifier, a
  relation addressed by the pair it joins -- =require-row-owner= reads that
  row's =created_by= and defers to =guard-owner= with it.
- A refusal *raises*, it does not emit: the handler's return value is what
  Artanis renders, so a route that emitted a 403 and then carried on would have
  it thrown away and answer 500 instead.  Both helpers raise the 403 that
  unwinds the route (=require-row-owner= a 404 first, when no such row exists).
  A route therefore only has to wrap its mutation in
  =(when (guard-owner ...) ...)= and cannot forget to refuse.
- Under both, =may-mutate?= in =(wikimusic controller)= answers #t for the
  super grant, and otherwise compares =created_by= with the session's
  =owner-id=.  A refusal is a 403, rendered by the same error pages as every
  other status.

Reading is not restricted: anyone may read any public row.  Only *writing* to a
row you did not create needs the super grant.

* Writing descriptions in Org mode

Every description field -- a song's, an artist's, a genre's -- is stored as
plain text and rendered as Org markup when the page is read.  The rendering is
done by [[https://codeberg.org/jjba23/orgwebalchemy][orgwebalchemy]], through the one function wikimusic exposes for it:

#+begin_src scheme
(org2html org-string)   ; (wikimusic html)
#+end_src

`org2html' turns an Org fragment into the SXML the rest of the page is built
from, so a description is styled by the same components as everything around it
and carries no raw HTML of its own.  It is called in exactly one place --
`entity-details', the shared detail block -- which means every entity that has
a description renders it the same way.

The syntax that reads well in a description:

- *#bold* and _/italic/_ words;
- =-verbatim= codes and ~monospace~ paths;
- nested bullet lists, with - or + or *;
- ordered lists, written 1. or 1);
- block quotes, wrapped in =#+begin_quote= ... =#+end_quote=;
- example and source blocks, =#+begin_example= / =#+begin_src=;
- and links, written =[[https://example.org][the words shown]]=.

A description is stored unescaped and rendered by orgwebalchemy, which escapes
what it emits; the field is therefore for prose, not for hand-written HTML.
The edit forms say so under the field itself, so a contributor need not read
this page to find out.

* Browsing the lists: sorting, tile size and search

Every list page -- =/songs=, =/artists=, =/genres= -- is the same grid of tiles
with the same three controls above it, and each control is an ordinary address
rather than a script.

- *Sort order* is a =select=.  Choosing one takes the reader to the same list
  with =?sort= in the query string, and the route remembers the choice in the
  =wikimusic-sort= cookie, so the next list opens the same way.
- *Tile size* is three icons -- small, medium and large -- in one small group.
  No page needs the words taking up room beside a list, so a size is shown as
  its icon alone: the words =Small tiles=, =Medium tiles= and =Large tiles=
  name each link to a reader who cannot see it, through the link's title and
  its accessible name, and the group itself is named to a screen reader.
  Following one takes the reader to the same list with =?grid-size=, which the
  route stores in the =wikimusic-grid-size= cookie.  Small is a dense wall of
  covers, large is a handful of wide tiles, and medium is the default; each
  size is a real address, so one can be bookmarked or shared.
- *Search* keeps its words with the other two: choosing a size or a sort while
  looking at results carries the search along instead of throwing the results
  away.

Every page is built from the same responsive shell, so these controls reflow
onto their own lines as the screen narrows, and no page -- list, detail or form
-- makes a phone scroll sideways to find the edge of the page.  The decorative
colour washes behind the page are anchored to the first screenful and clipped
to a layer of their own for the same reason: a decorative disc must never be
what a reader scrolls to.

* Guitar Pro 5 tablature

A song version may carry a *Guitar Pro 5* tab: the =.gp5= file the editors of
that generation write, and the tablature a reader can practise from in the
program that reads it.  A browser cannot open the file, so wikimusic holds it,
hands it back for download, and reads the file's own *header* to describe it on
the page.

** Uploading a tab

The =.gp5= is picked on the version form exactly as a PDF is: the browser turns
the chosen file into a data URL and posts that, and the row keeps it.  The file
field accepts =.gp5= files.

** What the page shows

When a version carries a tab, its section lists what the tab's own header
declares -- the title, artist and album its author typed, who tabbed it, its
tempo, its key, and how many measures and tracks the score holds -- and offers
the file for download under a name that says which song and which version it
is.  The facts come from the file and not from the row, so a reader can see what
the download holds before spending it.  A field the author left blank is left
out, and the numbers a readable header always carries are always listed.

** How much of the file is read

The reader stops at the counts of measures and tracks.  Everything a player
would play -- measure headers, tracks, beats, notes -- lies behind them and is
left where it is; those parts are long, version-dependent and structured, and
nothing the page shows needs them.  The reader is strict about its place in the
file: every string's declared length must match the bytes it occupies, and the
file must still hold as many bytes as the next field needs, so a file that does
not add up answers "the header of this tab could not be read" rather than a
guess.

A file the site cannot parse is still its author's file and is still offered
for download -- it simply carries no facts on the page.  A file of another
Guitar Pro generation is refused by the same header check, since its fields are
laid out differently.  The reader is written against the Guitar Pro 5 format,
and its module -- =(wikimusic guitarpro)= -- is the one place that knows the
file's byte layout.

** Seeing and hearing the tab in the page

The tab is not only offered for download.  Beside it is an offer to draw the
tablature in the page itself, notation and tablature staff together, and to play
it back: pressing the offer loads a *renderer* -- [[https://alphatab.net][alphaTab]] --
and draws the score, and the play control that appears with it plays the tab
through the browser's own audio.

Neither the renderer nor the sound it plays with is fetched until a reader asks
for a tab.  They are about two megabytes together, and a reader who came to read
about a song should not pay for a tablature they never open; a page whose tabs
are never opened costs a reader only the small script that offers them.  When a
reader does ask, the words describing what is happening -- loading, drawn, or
could not be drawn -- are the page's own: the view writes every sentence the
player can show and the script only un-hides one of them, so a translated page
stays translated while a tablature loads.

What the renderer and the sound are, where they came from, and the licences they
travel under are written down beside them in =pub/vendor/alphatab/README.md=.
They are fetched by =maak alphatab= and committed, so an instance serves its own
files and reaches no CDN at run time; raising the release in =maak.scm= and
running that task again is how they are updated.

A tab the site's own reader cannot follow is still offered to the renderer, and
a tab the renderer cannot draw says so on the page while leaving the file
downloadable: the two readers are independent, and a file that defeats one of
them is not therefore a file the site will not hold.

The list of file extensions artanis serves statically -- in =ENTRY= -- carries
=sf2= for the SoundFont, so a deployment that narrows that list should keep it.

* Export, archival, and exchanging between instances

Wikimusic can hand out *everything* it knows so that the whole corpus can be
archived, read offline, or loaded into another instance.  The unit of exchange
is the instance, not one entity: a share is how one wikimusic talks to another,
and a single file per side is what makes it a copy rather than a crawl.  Two
views of the same rows are offered, and one door back in.

The routes live in =app/controllers/interchange.scm=.

** The machine's view: a JSON dump

  GET /export/json
  #+begin_src sh
  curl -O https://wikimusic.example/export/json
  #+end_src

  The answer is =application/json= holding every content table row by row in a
  shape this same instance can read back:

  #+begin_src json
  {
    "format": "wikimusic-export",
    "version": 1,
    "exported-at": 1791907095,
    "tables": [
      { "table": "artists", "rows": [ { "identifier": "...", ... } ] },
      { "table": "songs",   "rows": [ ... ] }
    ]
  }
  #+end_src

  =tables= is a list in an order that respects the foreign keys among the
  tables, so an entity is always written before anything that points at it.
  Each row is the raw column values -- the dump is *not* rendered -- and the
  values are what a script or another instance reads back.

  The tables carried are the content itself: =artists=, =genres=, =songs=,
  their artworks, external sources and relations, a song's contents, and every
  entity's opinions and comments.  =users= and =password_reset= are
  deliberately absent: a share is a link to somebody's account, not a copy of
  it, and each row's =created_by= is resolved by the receiving instance on its
  own.

** The reader's view: a rendered HTML archive

  GET /export/html
  #+begin_src sh
  curl -O https://wikimusic.example/export/html
  #+end_src

  The same rows, as one long self-contained page: every artist, genre and song
  with its name linked to its page and its description already rendered from
  Org.  It is what an archivist wants -- a copy that reads in a browser with no
  server behind it -- and it links to the JSON dump above for the machine's
  copy.

** Loading a dump into another instance

  POST /import/json
  #+begin_src sh
  curl -X POST -H 'Content-Type: application/json' \
       --data @wikimusic-export.json https://other.example/import/json
  #+end_src

  The body is the JSON the export above produced.  Import is the one *write*
  here and the change is to the whole database, so it is gated: the session
  must hold =wikimusic:modify-permissions=, the super grant, and the route is
  never reachable anonymously.  Rows are inserted one at a time, and a row that
  fails -- a foreign key pointing at a user this instance does not have, or an
  identifier already taken -- is counted and skipped rather than aborting the
  share, so a partial import is still a partial success.  The answer says what
  happened:

  #+begin_src json
  { "format": "wikimusic-import", "inserted": 812, "skipped": 47 }
  #+end_src

  A table is only ever written if it is in the controller's fixed list of
  content tables, so a crafted body cannot reach a table of its own choosing.

For a whole-instance backup the SQLite file may simply be copied -- see
"Running Wikimusic" -- but the two export routes and the import are the
supported, format-stable way to move content between instances.

* When a page cannot be served

A reader who mistypes an address, follows a stale link, or meets a failure on
the server's side is shown a page of the site's own rather than the framework's
plain one.

The pages are built from the same document template, the same colour washes and
the same frosted pane as every other page, and they are rendered by the
application itself: a request that matches no route never reaches a controller,
and a handler that throws is already unwinding, so nothing in these pages may
depend on a route context.  The wording of a page is decided by its status
alone, which is why it can be read, and tested, without a server in front of it.

Each refusal is drawn in a tone that says what kind it is, leads with a
headline that says what happened in the reader's own terms, and follows it with
the sentence or two that says what to do about it:

- =400= -- the request arrived in a shape the server does not understand;
- =401= -- the page needs a signed-in reader;
- =403= -- the entry exists, but the reader's account may not read it;
- =404= -- no page answers that address, with links back to what is still
  there;
- =408= -- the request was still on its way when the server stopped waiting
  for it;
- =500= -- the server failed while building the page, and the source is linked
  with a report invited.

A status the table does not name is still rendered as a page rather than a
blank one: it is described by its class -- a wrong turn for another =4xx=, a
server failure for anything else -- over the code it actually answered with.
The registration happens once, in =ENTRY=, before the server takes its first
request, and the pages live in =app/views/error.scm=.

* On GNU Artanis

Find the documentation for Artanis here: https://www.gnu.org/software/artanis/manual/

GNU Artanis is the first production-level modern Web framework of Scheme programming language.

It is designed and maintained to be robust, fast, and easy to use for professional web development.

Here lies not just a framework, but a canvas where your ideas take flight with remarkable speed and grace. Artanis isn't about wrestling with complexity; it's about the joy of creation.

It's about harnessing the power of a robust and mature language to build something truly your own, something beautiful, nimble, flexible, powerful, efficient, understandable and maintainable. GNU Artanis was Certificated as Awesome Project at 2013 Lisp in summer projects.

One day, the folks at GNU were discussing what language they would write the GNU website in - and many chose Python. But I found that strange, because the official extension language of GNU is GNU Guile. And I wondered aloud - why not start a brand new project to provide a web framework written with GNU Guile? To which RMS said, "It's cool, I like this idea."

But at that time, it was just an idea without a plan.

Fortunately, a few months later, the Guile community held a hack-potluck to celebrate Guile2 turning two - which is a contest to write a cool program in a few weeks. And so, Artanis was born.

    1st January, 2015 - the first stable version Artanis-0.0.1 was released.

* On bundled third-party assets

wikimusic serves its own assets, and some of them are somebody else's work,
vendored into the tree rather than linked to, so that an instance reaches no CDN
at run time and works with no network of its own:

- *alphaTab* (MPL-2.0) draws a stored Guitar Pro tab as notation and tablature
  and plays it back;
- the *SONiVOX SoundFont* (Apache-2.0, © Sonic Network Inc.) is what makes a
  played-back tab audible, and fits beside it;
- *Bravura* (SIL OFL 1.1) is the music font a tablature is drawn with;
- *Intel One Mono* and *Plus Jakarta Sans* (both SIL OFL 1.1) are the two web
  families the interface is set in beside Lucida, and their licence texts
  travel with them;
- *Phosphor* (MIT) is the icon set every control on the site wears;
- the three *Lucida* families the interface is set in, and the *picture the
  project shows of itself*, which are the author's own files rather than a third
  party's -- what the project takes the position on the Lucida files to be is
  set out below, under *On Lucida fonts*.

Two tasks fetch them, and each is the only way its own files should change:
=maak vendor-assets= brings the typefaces, the glyphs and the project's picture
into =pub/= -- writing =google.css= and =phosphor.css= with every address made
relative on the way -- and =maak alphatab= brings the renderer, the music font
and the SoundFont into =pub/vendor/alphatab/=.  Their licences, their provenance
and the task that fetches them are written down beside the files, in
=pub/vendor/alphatab/README.md=, =pub/vendor/fonts/README.md= and
=pub/vendor/phosphor/README.md=.  They are unmodified, and their source stays
where it came from.

The rewriting a refresh does is the part of it that no fetch can be trusted to
show -- a copy that went on naming the host it came from would be a tree full of
files nobody reads -- so it is pinned by the test suite against a written
stylesheet rather than a live one, with no network: ~test/veritas/unit/assets-spec.scm~.

* On Reproducibility: Why GNU Guix?

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
