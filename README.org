The WikiMusic project is an non-profit community, with the goal of knowledge sharing and musical education, providing an open platform for exploring, sharing, and learning about music in all its forms.

If you like my work, please support me by [[https://bmc.link/jjbigorra][buying me a cup of coffee ☕]] so I can continue with a lot of motivation.

At its core, WikiMusic leverages the expressive power of Lisp (Guile Scheme) to build a dynamic interactive Music Gallery and Content Management System (CMS).

Whether you're a musician, educator, researcher, or simply a music lover, WikiMusic empowers you to:
- Discover music from diverse genres and traditions.
- Organize information with structured metadata and multimedia content.
- Contribute by adding new compositions, analyses, or educational materials.
- Learn through curated resources that connect music theory, history, and practice.

You can host your own version and database of WikiMusic, or visit the biggest one, mine over at:

[[https://wikimusic.jointhefreeworld.org][https://wikimusic.jointhefreeworld.org]]

WikiMusic leverages a database-backed architecture to ensure all content is easily searchable, linkable, and reusable. The user interface provides a seamless experience, inviting both beginners and experts to engage with the world of music collaboratively.

Join us in building an ever-growing library of musical knowledge — where every note tells a story.

* What Wikimusic offers

- *A gallery and a CMS in one*, built on Guile Scheme, GNU Artanis and SQLite,
  and written to be hacked: every piece of the interface is Scheme.
- *Songs, artists and genres*, each with a description written in Org mode,
  artworks, external sources, cross-references to the other entities, opinions
  and comments.
- *Song versions* that can carry an ASCII tab, a PDF, and a *Guitar Pro 5 tab*
  whose own header the page reads, which the page draws as notation and
  tablature, and which it plays back -- so a reader can see, hear and download
  the same file without leaving the page.
- *A responsive interface* -- the same shell on a phone and on a desktop -- with
  sorting, search and a subtle, icon-first tile-size control on every list.
- *Pretty error pages* for the refusals a reader actually meets (404, 403, 500
  and the rest), rendered by the application itself in the site's own shell.
- *Accounts and permissions*: sign-in, per-row ownership, and a super grant that
  overrides ownership for an instance's maintainers.
- *Everything out and back in*: a JSON dump of every content table and a
  rendered HTML archive of the whole instance, with an import route to load a
  dump into another instance.
- *Translated* into English, Dutch, Spanish and Japanese.

The [[file:docs/manual/en.org][manual]] covers each of these in detail.

* Development quick start

#+begin_src sh
# enter the project's environment (all dependencies, pinned)
guix shell -m manifest.scm

# create the database and add your first users (see the manual)
maak init-db

# run the site with hot reloading on http://localhost:50050
maak dev

# run the test suite
maak test
#+end_src

The [[file:docs/manual/en.org][manual]] explains the environment file a deployment
needs, the migration that adds users, and how to run Wikimusic as a daemon.

* On bundled third-party assets

wikimusic serves its own assets, and some of them are somebody else's work,
vendored into the tree rather than linked to, so that an instance reaches no CDN
at run time and works with no network of its own:

- *alphaTab* (MPL-2.0) draws a stored Guitar Pro tab as notation and tablature
  and plays it back;
- the *SONiVOX SoundFont* (Apache-2.0, © Sonic Network Inc.) is what makes a
  played-back tab audible, and fits beside it;
- *Bravura* (SIL OFL 1.1) is the music font a tablature is drawn with.

Their licences, their provenance and the task that fetches them are written
down beside the files, in =pub/vendor/alphatab/README.md=.  They are unmodified,
and their source stays where it came from.

Our core principle is simple: *AI should assist human creativity and problem-solving, never replace human reasoning.*

* On Reproducibility: Why GNU Guix?

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
